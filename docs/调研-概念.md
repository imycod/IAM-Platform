## SSO

### 你的场景

你说的是：

> admin.example.com   （后台）
cms.example.com     （CMS）

或者

> example.com/admin
example.com/cms

两个都是你自己的系统。

这其实叫：

> SSO（Single Sign-On）

而不是完整意义上的 OAuth Provider。

### Better Auth 完全可以

Better Auth 本身支持：
```
User
 ↓
Session
 ↓
Cookie
```
如果你的 Cookie 设置成

> Domain=.example.com

那么

> admin.example.com
cms.example.com

都能读取同一个 Session。

整个过程就是
```
用户
  │
  ▼
login.example.com
  │
  │ Set-Cookie
  ▼
Domain=.example.com
```
然后

> admin.example.com

请求

> GET /api/session

Better Auth

> session_id
 ↓
数据库
 ↓
User

得到当前用户。

CMS 也是一样。

所以：
```
登录一次

↓↓↓

两个系统自动登录
```
这就是 SSO。

## oauth2orize 是什么

oauth2orize 是很多年前 Node 的经典方案。

但是：

很多年没人维护
偏 Express
API 老
TypeScript 支持差
自己维护协议细节

现在几乎没人新项目会选它。

### 如果以后你的需求变成这样
例如：

```
你的 AI 系统

↓

允许第三方调用 API

↓

用户点击

"授权 XX 系统读取我的数据"
```

这就是

> Authorization Server

Better Auth 就不是最佳选择了。

通常会选择：

Keycloak
ORY Hydra
Authlib（Python）
Spring Authorization Server（Java）

这些都是专门做 OAuth2/OIDC 的。


只有当未来需要：

对外开放 API
第三方开发者接入
微信/飞书等外部应用授权
OpenID Connect（OIDC）
多租户 SaaS 对外授权

才建议单独部署一个 OAuth2/OIDC Authorization Server（例如 Keycloak、ORY Hydra 等）。

```
Client
   │
   │ authorize
   ▼
oauth2orize
   │
   ├── Authorization Code
   ├── Implicit（基本淘汰）
   ├── Client Credentials
   ├── Password（已废弃，不建议）
   └── Refresh Token
```
理论上实现：

  Authorization Endpoint
  Token Endpoint
  Client 管理
  Scope
  Refresh Token
  PKCE（需要自己补）
  用户登录
  Consent 页面

但是问题也很明显：

很老的项目（多年没有积极维护）
偏 Express 风格
TypeScript 支持不好
很多现代 OAuth/OIDC 特性需要自己实现
需要自己维护安全细节

OAuth/OIDC 协议本身很复杂，自己维护协议实现的成本和风险都不低。

### 一、先纠正一个常见误区

很多人会这样设计：
```
User 表：
  role: admin
```
或者：
```
Profile 表：
  role: manager
```
❌ 这是错误的企业级设计

原因：

- 一个用户可以有多个角色（多应用、多租户）
- 角色是“上下文相关”的（workflow/admin 不同）
- role 本质是关系，不是属性

### 标准 Access 模型
```
User
  ↓
ApplicationUser（能否进入系统）
  ↓
Access Domain（权限域）
  ↓
Role Assignment（角色分配）
  ↓
Policy / Permission（能力）
  ↓
CASL（是否允许 + 数据范围）
```

## Identity

User、Account、Auth (一步到位：人 + 能登录的账号一起建。)

先记一个核心：一个人 + 多种登录方式
可以把系统想成两层：

概念	通俗说法	存什么
用户（User）
这个人是谁
邮箱、姓名、手机、状态
账户（Account）
这个人怎么登录
密码登录、微信登录、Google 登录……
一个人（User）可以挂多个 Account，比如：

credential + 邮箱 → 密码登录
wechat → 微信扫码登录
google → Google 登录
Account 不是「登录各个业务平台」，而是「登录 IAM 本身用的各种方式」。
