## 一、Identity（身份）

只负责: 用户是谁, 不负责权限

```

Reset Password
```

```

```

## 从用户登录到访问应用的完整流程
```
用户访问 Workflow
        │
        ▼
IAM (node-oidc-provider)
        │
        ▼
Identity/Auth（Better Auth）
        │
        ▼
Identity/User（确认用户身份）
        │
        ▼
Organization（加载部门、团队等组织信息）
        │
        ▼
Application（确认用户是否允许访问 Workflow）
        │
        ▼
Access（计算角色、权限、菜单、数据权限）
        │
        ▼
Security（签发 OAuth2/OIDC Token、记录审计、应用安全策略）
        │
        ▼
Workflow 收到 Access Token
        │
        ▼
后续 API 请求携带 Token，按 Access 模块提供的权限模型进行授权检查
```
### 还有一点我会和大多数教程不一样（也是我最推荐给你的）
不要让 role、user、application 等模块直接互相注入。
```
UserModule
    imports: [RoleModule]

RoleModule
    imports: [UserModule]
```

最后就变成：
```
forwardRef(...)
```
满天飞。
### 我建议采用依赖方向固定的方式：

```
Identity
        │
        ▼
Organization
        │
        ▼
Application
        │
        ▼
Access
        │
        ▼
Security
```
或者更准确地说：

identity：只负责"用户是谁"。
organization：给用户挂组织信息。
application：定义有哪些业务系统。
access：给应用配置角色、菜单、权限。
security：负责 OIDC、OAuth Client、Token、审计等。

这样模块职责单一，依赖方向清晰，后续接入 node-oidc-provider、拆微服务或增加新系统时都不会陷入循环依赖。

需要澄清的边界（否则会出问题）
1. identity/auth 和 security/oidc 之间谁做什么，必须写死
这是最容易踩坑的地方。按我之前的架构：

identity/auth：封装 better-auth，负责"校验账号密码/MFA 是否正确"——纯粹的认证逻辑，不知道 OIDC 协议
security/oidc：封装 node-oidc-provider，负责签发 code/token、管理 SSO session——纯粹的协议逻辑，不知道密码怎么校验的

中间缺一个桥接层（我之前叫 interaction），职责是：接住 node-oidc-provider 抛出来的 /interaction/:uid 请求 → 调 identity/auth 校验 → 调 security/oidc 的 interactionFinished()。
在你这个结构里，这个桥接逻辑归属不明确。建议要么在 identity/auth 下加一个 interaction 子模块，要么在 security/oidc 下加，但不要让 identity 和 security 互相直接依赖对方的实现细节，只通过这一个桥接点交互，否则两个域会缠在一起。
2. application 和 security/oauth-client 是强 1:1 关系，但分在两个域里
application（workflow、admin 这些接入系统的元数据）和 oauth-client（对应的 client_id/secret/redirect_uris）本质上是同一个东西的两个面。分开放的好处是"业务信息"和"安全凭证"权限隔离（比如查看 application 列表不需要看到 client_secret），但要注意：

建库表时 oauth_client.application_id 要外键约束到 application.id
代码里要明确"谁是权威来源"——建议 application 模块只存业务元数据，client_secret 之类敏感信息完全由 security/oauth-client 模块管理和加密，两者通过 application_id 关联，不要冗余存储

3. token 和 identity/session 可能语义打架
security/token 大概率对应 node-oidc-provider 的 access_token/refresh_token（协议令牌），而 identity/session 对应 better-auth 的门户会话（登录态）。这是两个完全不同的东西，但命名上容易让新人搞混——"我登录了，为什么还有 session 又有 token？" 建议在文档里明确写一句话：

session = 你在 auth.example.com 门户内的登录态；token = 下游系统(workflow/admin)拿到的、代表你身份的凭证

4. 没看到"外部身份联邦"(微信/飞书)的落点，但其实不需要新建域
好消息是不用加新模块——identity/account 本身就该承担这个职责（account 表 provider_id 可以是 credential/wechat/feishu），未来对接微信飞书时，只是在 identity/account 下多实现一个 OAuth2/OIDC client 策略，不需要动整体架构。如果你们觉得联邦登录逻辑会比较重（比如要维护多个 IDP 的 discovery、jwks 缓存），也可以单独拆一个 identity/federation 子模块，但没必要现在就拆。
5. organization 和 access 的关系要想好
部门/团队是否参与权限判定？比如"部门经理"这个角色是否等于"该部门下所有人的数据权限"？如果是，那 access/policy 的条件表达式就需要能引用 organization 域的数据（比如 department_id in current_user.managed_departments）。这是个跨域依赖，建议 organization 域对外暴露一个"获取用户管理范围"的接口，而不是让 policy 引擎直接查 organization 的表。
